# PDF assets and authenticity

SolidPDF exposes document metadata, embedded files, portable collections, and signatures as inert typed values. Reading an asset inventory never decodes attachment bodies. Opening an embedded file is a separate, explicit operation that uses the document's bounded decoded-stream pipeline. Filenames and file-system declarations are metadata; SolidPDF never converts them into host paths, opens them through the external-stream provider, launches them, or executes associated actions.

`PDFDocument.metadata()` reconciles Info and XMP values without discarding either source. `PDFDocument.assetInventory()` combines that metadata with attachment summaries, associated-file relationships, collection metadata, and byte-free signature descriptors. Callers must explicitly request `decodedStream(of:)` or `decodedBytes(of:)` for an embedded file.

Signature validation deliberately has no single validity Boolean. `PDFSignatureValidationResult` reports these dimensions independently:

- source coverage and unsigned revisions or trailing bytes;
- cryptographic digest and public-key integrity;
- certificate trust against the selected provider;
- offline revocation evidence;
- authenticated or trusted timestamp evidence;
- DocMDP and FieldMDP post-signing modification permissions.

Cryptographic integrity is evaluated even when no trust provider is installed. In that case trust is `notEvaluated`. `PDFOfflineSignatureTrustProvider` uses only caller-supplied DER anchors, intermediates, and evidence. It never consults the host trust store, follows AIA links, or performs OCSP, CRL, certificate, or timestamp network requests. A custom `PDFSignatureTrustProvider` receives immutable certificate and evidence values but no PDF source, filesystem, or network capability.

Signatures and attachments remain inspectable when invalid or untrusted. Signature container bytes, attachment bytes, password fields, JavaScript, XFA, and actions are never included in ordinary page-text extraction.

The fixtures generated by `Scripts/generate-pdf-authenticity-fixtures` use project-only credentials under a caller-selected output directory. They exist solely for differential testing with OpenSSL, qpdf, Poppler `pdfsig`, MuPDF, and ExifTool and must never be used as production trust material.
